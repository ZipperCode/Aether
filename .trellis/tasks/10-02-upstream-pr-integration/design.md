# 技术设计

## 阶段边界

1. **上游基线阶段**：仅处理 `master` 与已 fetch 的 `upstream/main`。先使用合并树、冲突文件和提交主题建立冲突清单，再执行实际 merge；冲突按本地功能与上游行为逐文件解决。
2. **基线验证阶段**：上游合并形成提交后，验证冲突集和上游近期改动覆盖的关键模块。重点覆盖 gateway、formats、provider-pool、data/postgres、integration、frontend。
3. **PR 评估阶段**：在新的合并提交上评估 PR，而不是在旧 master 上判断。优先使用 PR head/base 的真实 diff，确认上游是否已经包含等价变更。
4. **PR 集成阶段**：按依赖和冲突风险一次纳入一个 PR。对同一候选选择语义（#857/#874）先统一领域规则再集成，不保留冲突兼容层。

## 关键不变量

- 候选选择的 scheduler-core、memory repository、Postgres SQL 三处规则必须保持一致。
- 格式转换必须保留客户端声明的工具语义，不能把可由客户端执行的函数调用转换为 hosted call。
- 流式预读取交接不能丢字节或解析器状态；已合入上游的 #858 与 #840 不能叠加假设。
- Codex/Claude 客户端画像的版本、UA、OAuth scope、额度查询与 provider transport 使用同一有效画像，旧调用点要随结构迁移。
- 本地已有的模型、配额、图片、计费和权限行为不得因机械保留本地版本而回退。

## 冲突处理策略

- `.github/workflows`：保留当前项目 CI 安全边界，同时吸收上游 scope 检测与任务拆分；以实际 workflow YAML 检查为准。
- Cargo manifests/lock：保留 workspace 依赖闭包和上游新依赖，完成 `cargo check`/目标测试验证。
- gateway/fmt/scheduler：以行为和测试为主，优先保留本地已落地的业务修复，再引入上游独立能力。
- frontend：按组件/接口类型/测试一起迁移，避免只解决模板冲突而丢失 API 合同。
- migration/schema：不手工改生成目录；若上游迁移与本地迁移编号/基线重叠，保留唯一可追踪迁移并做 schema 测试。

## PR 选择标准

- **纳入**：未被上游覆盖；改动与合并基线无不可控语义冲突；能够完成针对性验证。
- **暂缓**：需要大面积手工重写、与本地已有功能重复、缺少运行证据，或依赖另一个未纳入 PR。
- **拒绝/已覆盖**：上游已有等价实现，或 PR 的原问题已由后续合并修复。

## 回滚

每个阶段使用独立提交。若某个重点 PR 验证失败，保留上游合并提交及此前成功的 PR 提交，不继续叠加失败 PR；必要时在当前任务内回退该单独提交，不触碰用户无关改动。
