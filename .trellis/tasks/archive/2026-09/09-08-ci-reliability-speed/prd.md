# 优化 GitHub CI 可靠性与编译耗时

## Goal

减少本地代码进入 GitHub Actions 后反复修复的次数，缩短有证据的 CI 编译关键路径，并解释是否由功能体量导致。

## Confirmed Scope

- 用户明确要求优化；调查后在可本地验证范围内直接实施，不新增独立实施确认。
- 本地起点 `798ba9d5c8166febab1ab3c56b29f93f17d0e6ee`，工作区干净；GitHub master 仍为 `876a4fb5a95a95d9ccd6493b818176ae53e87eeb`。前一任务完整上游合并尚未推送。
- 先分别审计真实 CI 失败/耗时与当前工作流/本地检查调用链，区分历史远端和当前本地事实。
- 不删除业务功能，不减少既有必要测试、数据库契约或精确 SHA 发布门禁，不以取消检查伪装加速。
- 不启用付费 runner、不修改仓库权限/secret/共享设置、不 push/dispatch CI/发布/部署；远端实测需要后续授权，不能声称本地改动已有 GitHub 加速实测。

## Requirements

1. 依据最近失败与成功运行的 job/step 证据归因，不把所有失败泛化为“功能太多”。
2. 修复确有证据的本地/CI 命令、工具链、feature/profile、测试夹具或快速门禁漂移；仅处理当前请求关联的构建问题。
3. 优先消除重复构建、无效失效与缓存/并行关键路径浪费，复用项目现有工具和依赖；不默认增加新构建基础设施。
4. 改动拥有可运行的最小验证，保留现有覆盖；实际速度收益和只属结构性预期必须区分。

## Acceptance Criteria

- [x] 保存带 run/job/step/commit 定位的失败分类和耗时基线。
- [x] 实施经证据筛选的最小优化，不变更功能和必要门禁。
- [x] 配置/脚本解析与针对改动的回归通过；无必要时不重复完整 Rust/UI 测试。
- [x] 提供现有本地可执行的 CI 对齐检查入口或更新既有入口，避免再次依赖记忆拼命令。
- [x] 解释性能瓶颈、实际修复、验证及尚需 GitHub 运行确认的边界；清理本任务临时产物。
